Vocabulary & Contracts

Prompt
Authored instruction text — the template a person or system writes and versions, before anything is assembled around it. Distinguished from: context. A prompt is one component rendered into context alongside history, tool schemas, and retrieved data — not the assembled whole. (Defining a prompt as “instructions plus context” while defining context as something containing the prompt is circular; these two entries deliberately avoid that.)
Instruction
A directive telling the model how to behave. Carries an authority rank by the message type it arrives in — platform/system outranks developer, which outranks user. Note: tool outputs and retrieved content carry no instruction authority; they are data, however imperative their wording. Distinguished from: a message, which is one turn's content whether or not it instructs.
Message
One turn's content in the conversation format APIs exchange — a role (system/user/assistant/tool) plus content. The unit conversation history is built from.
Context
The set of tokens included when sampling from the model for one call — the rendered prompt, tool schemas, retrieved data, history, examples. Distinguished from: everything the application stores (that is state or memory). Context is only what is assembled into this specific inference call.
State
Durable data recording where a run has got to — step reached, checkpoints, pending waits, partial results committed so far. Progress, not knowledge. Distinguished from: memory, which records what the run knows. Rule of thumb: state is what you need to resume a run; memory is what you need to inform one.
Memory
Retained information (facts, preferences, learned routines, past runs) pulled selectively back into context, never dumped wholesale. Distinguished from: state (progress toward completion) and context (the tokens for this one call).
Tool
A function the model can request be called, with a schema, arguments, and a result — the model's only way to act beyond producing text.
Resource
Application-controlled data attached to give the model context (file contents, records) — the client decides what's attached, not the model and not the user directly. Per the MCP specification (revision 2026-07-28), resources are application-controlled, distinct from user-controlled prompts and model-controlled tools.
Skill
A packaged, reusable capability (instructions, and often tools) an agent can invoke for a specific kind of task, without rebuilding that capability from scratch each time.
Agent
A model plus instructions plus tools, run by a runtime loop that keeps calling the model until a task is done. Distinguished from: a workflow — see below.
Workflow
A system where the model and tools are orchestrated through a predefined code path — the sequence of steps is fixed in code. Per Anthropic's framing, an agent by contrast is a system where the model dynamically directs its own process and tool use.
Harness
The orchestration and scaffolding layer — decides what happens next: assembles context, selects and dispatches tools, applies stop conditions, runs the loop. Distinguished from: runtime. A harness is logic; it runs on a runtime.
Runtime
The execution environment and lifecycle infrastructure — decides where and how it actually runs: processes, state persistence and checkpoints, queues and concurrency, timeouts, cancellation, retries, telemetry plumbing. Distinguished from: harness. In casual use the two get used interchangeably, and elsewhere in this reference “harness” sometimes stands in for both; they are separable, and separating them is what makes a run durable rather than merely orchestrated.
Session
A continuous span of interaction with a user — may contain multiple runs.
Run
One complete execution of a task from start to finish — may span many turns and many steps.
Turn
One exchange between user and system — one user message plus the system's full response to it (which may itself involve several steps).
Step
One iteration of the agent loop within a turn — one model call plus whatever follows it (a tool call, a decision, or a final answer).
Trajectory
What a run actually did, as far as it is observable: the sequence of messages, tool calls and their results, state transitions, and artifacts produced. Reasoning counts only where deliberately exposed — internal reasoning may be unavailable, partial, or an unfaithful account of what drove the behaviour, so treat it as evidence, not ground truth. Graded separately from the outcome, since a run can reach the right end state the wrong way, or the reverse. Distinguished from: a trace — the trajectory is the behaviour; the trace is the recording of it.
Trace
The instrumented recording of a trajectory, emitted by observability tooling — spans, timings, token counts, and the prompt/model/harness versions in play. Distinguished from: trajectory. A grader reasons about the trajectory; it reads a trace to do so. Two runs can share a trajectory shape and still produce very different traces (different latencies, costs, versions).
Artifact
A durable output produced during a run (a file, a report, a result) — persists after the run ends. In the A2A specification, tasks produce artifacts as their defined output, each built from typed content parts.
