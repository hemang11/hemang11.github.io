The outer system turns a probabilistic model call into a useful, controlled, secure, stateful, observable, reliable, and economical product. The L1–L4 stack below is a reference topology — the usual shape of a managed-provider deployment, and a map for reasoning about who owns what — not a required architecture. The hop count on each block shows how far that layer sits from the model itself in this topology — only L4 ever calls it directly. Underneath all of it sits a model gateway: providers return many different response shapes, and the gateway normalizes them into one canonical response envelope — a common shape that preserves the information rather than throwing it away — which is what the harness above is written against.

Read the four layers as a reference topology, not a mandate. This is the common shape when you call a managed provider over the network, and it is useful because it separates concerns that really are separate. But deployments vary: a local or self-hosted setup can collapse L3 and L4 into a single process, or collapse all four into one program with no network boundary anywhere, in which case the hop counts stop describing anything physical. Treat the hop count as distance from the weights in this picture, not as a count of required network boundaries.

A production system adds a further layer: deployed agent system = agent + runtime + memory/data + permissions/policies + interface & operations. The Runtime piece above is the execution environment and lifecycle infrastructure — state persistence and checkpoints, tool execution and sandboxing, validation plumbing, telemetry, concurrency, timeouts, cancellation. Harness is a different thing: the orchestration logic that rides on that runtime and decides what happens next — loop control, context-assembly decisions, tool selection, stop conditions. The two are separable concerns that happen to co-locate at L2, which is why the block above is labeled Harness & Runtime; see the Vocabulary page for the full distinction.
DISTINCTION

Workflow vs. Agent

Workflow
fixed, code-defined path — the same steps every time
Agent
model dynamically decides what to do next
Not everything that loops is an agent — a workflow follows a path defined in code. Anthropic defines workflows as “systems where LLMs and tools are orchestrated through predefined code paths,” and agents as “systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks.” Most production systems are hybrids of both: fixed steps where the path is known, agentic judgment where it isn't. (Source: Anthropic, “Building Effective Agents.”)

Providers differ, and no response can honestly be reduced to three cases. A single response may carry mixed multimodal content, schema-constrained structured output that is not a tool call, or several tool calls at once; it may end for any of a range of finish reasons (completed normally, hit a length cap, tripped a content filter, was cancelled); it may arrive as a stream of events rather than one atomic object; it reports token usage; and a transport/API-layer error is a different category from a model refusal. So the gateway's job is not to collapse all of that into text / tool call / refusal — three mutually exclusive outputs cannot carry ordered multimodal parts, N tool calls, usage, and a finish reason at the same time. Its job is to normalize every provider into one common envelope shape while preserving the information: an ordered list of typed content parts; an optional structured payload; zero-to-many tool calls; a finish reason; a safety/refusal status carried as a field on the envelope rather than as a rival category to text; usage; and a separate error field for transport/API failures. That envelope is something your gateway/adapter layer creates and maintains — not something a model or provider hands you — so the harness above it can be written once instead of once per provider. The gateway is also where the model's bounds (input modalities, context length, max output tokens) are surfaced as one predictable set of limits, and where model selection, routing, version pinning, and fallback compatibility live — never inside the model itself. One thing the gateway cannot normalize away: sampling, which means the same input can legitimately yield different output from one call to the next.
