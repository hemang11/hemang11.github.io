Security, Human Control & Governance

Two different failure modes, one page. A Guardrails failure is an unsafe output or action slipping through in the moment. A governance failure is nobody being able to say who did what, on whose authority, and whether it could be undone. Runtime gates check individual outputs and actions; the policy layer beneath them establishes identity, scope, and an audit trail for everything the agent does on someone's behalf.

Two different gates on two different timing rules. Content moderation can run concurrently with generation, so the classifier isn't serialized in front of it — but concurrent isn't free: it still costs, it may mean buffering output instead of streaming it straight through, and if a classifier trips mid-stream the in-flight generation gets cancelled and the already-generated text withheld. So it gates delivery, not generation — the content may exist and still never reach the user. Authorization for a consequential action (send, pay, delete) is a different rule: it must fully complete before that action executes — it is never parallelized away.

This is the cross-cutting layer above the runtime gates: it establishes who or what the agent is acting as — a real, traceable user or service identity, never an anonymous actor — and scopes every permission to the minimum the task needs, so one tenant's agent or data can never reach into another's. It's the layer that guardrails, authorization, and sandboxing (see the Guardrails card and the Tools & Agents page) exist to defend against three named risks: prompt injection (untrusted content steering the model into unintended actions), data exfiltration (sensitive data leaving through an unexpected channel, e.g. embedded in an innocuous-looking tool call), and memory/tool poisoning (an attacker corrupting stored memory or a tool's output so a later step is misled). Whether an action needs human approval is a policy decision rather than a single test: it weighs consequence and blast radius, data sensitivity, scope (one record or a bulk operation), the recipient or destination (internal vs. external, known vs. unknown party), the delegated authority the acting identity actually holds on the principal's behalf, and explicit org rules that can require approval regardless of the rest. Reversibility is one important input among those, not the whole test — which is why a reversible action can still require approval: a bulk edit touching sensitive records, or anything crossing an external boundary. That's not a contradiction — undoing an action doesn't undo who saw the data. Every consequential action is logged — who, what, when, on whose authority — with retention and data-residency requirements enforced centrally here, not left to each tool to handle inconsistently.
