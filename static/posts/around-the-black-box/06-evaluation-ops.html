Evaluation, Observability & Operations

Two different practices meet on this page: evaluation asks whether the agent is actually good — offline, on curated cases before a change ships, and online, on real production traffic afterwards — and operations asks whether the deployed system is healthy right now. The two halves of evaluation are complementary, not sequential, and neither works without operations: the traces and metrics operations collects are the same raw material an offline suite replays and an online grader scores.

Final text alone under-grades an agent: work happens across many turns of tool calls and state changes, and mistakes can “propagate and compound” across turns — while frontier models sometimes find creative solutions that beat a static eval’s expectations, so grading only the output risks both false negatives and missing genuine progress. Anthropic recommends measuring outcome and trajectory separately: outcome is the actual environmental state — did a reservation really get created in the database, not just did the agent say it booked one — while trajectory is the observable record of the run: the messages, the tool calls and their results, the state transitions, and the artifacts produced, plus the model’s reasoning only where it is deliberately exposed. A grader can only see what the system actually exposes; internal reasoning may be unavailable, partial, or not a faithful account of what actually drove the behaviour, so it is evidence rather than ground truth about the model’s process. Trajectory is where questions like whether a support agent stayed within turn limits or behaved appropriately get answered — dimensions the final state alone can’t measure. Measuring the two separately is the right default, because one blended score hides which dimension failed; combining them afterwards is legitimate once they have been measured separately — a release gate can require outcome-pass and trajectory-pass, and a weighted aggregate can be tracked over time — provided the per-dimension results stay preserved and inspectable. Deterministic, code-based grading fits best where success is objectively checkable, especially for coding agents; for non-deterministic outputs, run multiple trials and report pass@k (at least one success in k attempts) and pass^k (all k attempts succeed) — a 0% pass rate across many trials “is most often a signal of a broken task, not an incapable agent.” Where an LLM-as-judge grades instead, it must be closely calibrated against human experts, score each dimension separately against a structured rubric instead of collapsing straight to one holistic number, include an “Unknown” escape hatch for low confidence, and get periodic — not constant — human review once the system is proven. Red-team with balanced problem sets that test both where a behavior should and shouldn’t trigger, and design evals agents “shouldn’t be able to easily ‘cheat,’” using adversarial user personas (Anthropic cites τ2-Bench) to stress-test conversational agents through extended, adversarial conversations. (Source: Anthropic, agent evaluation guidance.) This is the offline half of the practice only — a curated suite scores a fixed set of cases someone thought to write down, which is why it pairs with online evaluation on live traffic rather than standing alone as a ship gate.

The “offline suite” is really two instruments answering two different questions, and using one as the other is why teams get surprised. A regression suite asks did we break something that used to work? It is built from cases the system already passes — including specific past failures captured as tests once they were fixed — so its expected pass rate is essentially 100%, and any failure is a signal to act on. That is what makes it usable as a release gate. It grows monotonically and gets cheap to run, and its weakness is that it only covers ground you have already walked: it can be entirely green while the system is bad at everything nobody thought to write a case for. A capability suite asks can the system do this at all, and how well? It is built from hard, representative, often currently-failing cases that describe the target rather than the status quo, so a partial pass rate is the normal and useful state — the number is a benchmark to move, not a threshold to clear. It is what tells you whether a model, prompt, or harness change bought real capability. Its weakness is the mirror image: it is noisier and more expensive, and a rising score does not prove that nothing regressed. Anthropic draws exactly this split — capability evals “should start at a low pass rate, targeting tasks the agent struggles with and giving teams a hill to climb,” while regression evals “should have a nearly 100% pass rate” and “protect against backsliding.” You need both, because substituting one for the other fails in a specific way: gating releases on a capability suite blocks shipping on cases that were never passing, and judging progress by a regression suite tells you only that you have not gone backwards, which is not the same thing as having got better. The two connect by graduation — Anthropic notes that capability evals whose pass rates have risen can “graduate” into a regression suite run continuously, and the same move applies to a fixed bug, which becomes a permanent regression case. Both suites want multiple trials rather than a single run, and a capability suite most of all: partial success is its expected state, so pass@k and pass^k carry information one attempt cannot. And both are still offline — drift means a green regression suite and a climbing capability score can coexist with live behaviour degrading on traffic neither suite contains, which is why online evaluation sits alongside them.

A passing offline suite is not evidence that the live system is fine. Anthropic frames automated evals, production monitoring, A/B tests, user feedback, and transcript review as complementary methods — so evaluation continues after the change ships, and it runs on the same traces operations is already collecting. Production sampling continuously pulls real traffic and grades it, instead of only re-scoring curated offline cases. User feedback supplies two kinds of signal: explicit (thumbs, reports, ratings) and implicit (abandonment, retries, users correcting or rewriting the agent's output) — the implicit ones are often the earlier warning. Distribution drift is the reason this matters: the real input distribution keeps moving away from whatever the offline suite covers, so the suite can stay green while live quality degrades on inputs it never contained. Shadow evaluation runs a candidate version against real traffic without serving its output, so it can be compared on realistic inputs before any user is exposed to it. A/B testing then compares versions on live traffic against real outcome metrics — task completion, escalation rate, cost per successful task — not just grader scores. Transcript review keeps humans reading actual production trajectories, which is what surfaces failure modes no pre-written eval anticipated; each one found becomes a new offline case, which is how the two halves feed each other.

Building the agent is not the same as running it. Every model call, tool call, and decision gets traced, and latency is decomposed by layer — harness, transport, inference, tools — instead of reported as one aggregate number, so a slowdown can be located rather than just noticed. Cost is tracked per successful task, not per call: a cheap call that fails and needs retries can cost more per completed outcome than an expensive call that works the first time. Alerts fire on defined SLOs, not raw error rate alone, and every trace carries version provenance — which prompt, model, and harness version produced it. Changes get canaried before a full rollout, and rollback stays fast and cheap. When an incident hits, response works because the tracing, metrics, and version provenance already exist — not because someone starts investigating from zero. Retention, privacy, and data-residency requirements apply to traces and logs the same as they apply to primary data. Those same traces are what online evaluation samples and grades — operations collects the evidence, production evaluation scores it.
