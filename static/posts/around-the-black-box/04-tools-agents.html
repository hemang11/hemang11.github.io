Executing a tool is what step 4a of the loop above actually does, and it is a lifecycle rather than one action. Discovery is how the agent learns a tool exists — load schemas on demand rather than stuffing every schema into context. A tool's description and JSON Schema are what the model reasons over, so ambiguous ones cause misuse. Then, before anything executes: validate arguments against the schema, because the model's arguments are never trustworthy; the call runs as a specific identity with scoped permissions, checked before execution rather than after; and the runtime brokers secrets, injecting credentials at call time so they never enter model context. Side-effect classification — read-only vs. mutating vs. irreversible — drives everything downstream: whether a call needs an approval gate with a human in the loop, whether a dry-run should preview what would happen before doing it, what timeout bounds it, whether an idempotency key is required so a retry can't double-execute a mutation, and what the retry policy is. Two things are easy to get wrong here. First, read-only does not mean free to repeat: it means no external state is mutated. A read can still consume quota, trigger metering or billing, hit a rate limit, and return a non-repeatable result — a paginated or time-sensitive read can legitimately differ between attempts, so a retry is not automatically equivalent to the first call. Retries therefore need a budget, backoff, and the assumption that the second answer may not match the first. Second, “undo” is not universally available, and designing as if it were is the actual error. A compensating action works only where a semantically inverse operation exists — refund a charge, cancel a booking. You cannot un-send an email, un-publish a post, or un-disclose data. For genuinely irreversible effects the real answer is prevention before execution (an approval gate, narrowly scoped permissions and arguments), then reconciliation — detect and record the divergence between intended and actual state — and forward recovery: an action that moves to an acceptable state, such as sending a correction notice, rather than pretending to roll back. Execution itself is sandboxed with egress control, so a compromised tool can't reach the network to exfiltrate. Afterwards the raw output is normalized into a consistent model-consumable shape and truncated so one huge result can't blow the context window, and the call — its arguments, its identity, its outcome — is audited. MCP is explicit that even a tool's own metadata is untrusted, not just its output: “clients MUST consider tool annotations to be untrusted unless they come from trusted servers.” Two changes in MCP protocol revision 2026-07-28 (the revision this page is pinned to) land directly on this lifecycle. MCP is now stateless — “MCP has no protocol-level session, so a server cannot rely on implicit per-connection state” — so a server that needs state across calls returns an explicit opaque handle from a creation tool and accepts it as an ordinary argument on later calls, and it should validate the caller’s authorization against that handle on every call (the spec says SHOULD; treating it as mandatory is this reference’s recommendation, not a spec requirement): a handle is a name, not a capability. Authorization and idempotency therefore become per-call checks rather than per-session assumptions — there is no session for either to hang on. And Multi Round-Trip Requests give the approval/elicitation gate above a protocol-level form: rather than calling back to the client, a server returns an InputRequiredResult (resultType “input_required”) whose inputRequests field says what it needs, and the client retries the original request with inputResponses.

The Critic agent checks the Worker's draft against criteria. Rejected work loops back for another attempt; approved work ships. Three things this pattern requires to be safe: the iteration count must be bounded — never loop forever; the acceptance criteria must be measurable, because a vague “is it good?” critic can't converge; and there must be an escalation path when convergence fails — hand off to a human or fall back, rather than spinning. That's the same bounded-retry-plus-separate-escalation policy shape as Failure & Recovery on the State & Runtime page. Use when correctness matters more than speed — a second opinion catches what the worker misses.

Anthropic's building-effective-agents guide names five patterns. Two are already diagrammed above and are only cross-referenced here rather than re-drawn: Orchestrator-Workers (a central LLM dynamically decomposes a task and delegates to workers — the Fan-out shape above) and Evaluator-Optimizer (one LLM generates while another critiques in a loop until criteria are met — the Worker + Critic shape above). Prompt Chaining is sequential LLM calls, each processing the prior step's output, with optional checkpoints between. It shares a sequential shape with the Pipeline / Handoff card above, but the two are not the same thing and shouldn't be equated: chaining is about sequenced calls, and several of those calls can live inside one agent — it does not inherently require multiple agents with separate tool-sets, which is what a handoff pipeline is. The remaining two Anthropic patterns are Routing — classify an input, then direct it to specialized downstream handling built for that category — and Parallelization, which has two variants: sectioning splits a task into independent subtasks run at once (again the Fan-out shape above), while voting runs the identical task several times and aggregates the results for confidence. Beyond Anthropic's five, three more shapes are common across agent frameworks generally. Plan-and-Execute: the agent first produces an explicit plan, then executes its steps, typically re-planning when a step fails or reality diverges from the plan. What separates it from plain chaining is that the plan is a first-class artifact the agent generates at run time, not a path fixed in code. Shared Workspace: agents read and write one common piece of state instead of passing messages directly to each other. Hierarchical Supervision: a supervisor agent continuously monitors workers and can interrupt or redirect them mid-task, not just dispatch them once.

Agent→tool calls all carry the same three things — a tool name, arguments, and a result — but there are several formats for saying it, and they stack rather than compete. Native provider function calling is the floor: each provider defines its own tool-calling format, with tool declarations in the request and tool-call blocks in the response. That is the baseline every gateway or adapter normalizes, translating one internal tool definition into whichever provider shape is in use. OpenAPI-to-tool adaptation goes the other direction: generate tool schemas directly from an existing OpenAPI/REST description, so services that are already documented become callable without hand-written wrappers — the description you already maintain becomes the tool contract. MCP standardizes the client/server side, so one tool server can serve many hosts instead of each host writing its own integration, and it further splits what a server exposes into three primitives by who controls them: Prompts are user-controlled — interactive templates invoked by user choice (slash commands, menu options); Resources are application-controlled — contextual data the client attaches and manages (file contents, git history); Tools are model-controlled — functions exposed to the LLM to take actions (API POST requests, file writing). The MCP detail here is pinned to protocol revision 2026-07-28 and was checked on 2026-07-30 — MCP is versioned by dated revision, so revision-specific detail on this card will drift as new revisions publish. Three changes in that revision alter the shape of tool integration. MCP is now stateless: protocol-level sessions and the Mcp-Session-Id header are removed and the initialize / notifications/initialized handshake is gone, with each request instead carrying its protocol version and client capabilities in _meta, so a server needing state across calls returns an explicit opaque handle from a creation tool and re-authorizes the caller against it on every call. Multi Round-Trip Requests (MRTR) replace server-initiated requests: a server returns an InputRequiredResult (resultType “input_required”) whose inputRequests field carries what it needs, and the client retries the original request with inputResponses — every result now carries a required resultType of either “complete” or “input_required”. And servers SHOULD return tools from tools/list in a deterministic order, which “enables client-side caching and improves LLM prompt cache hit rates” — a stable tool block is a cacheable prompt prefix, the same point the Foundations and Context pages make about prefix stability. Migration warning: tasks — durable requests that outlive a single request/response — are no longer a core feature. In revision 2026-07-28 they moved out of core into an official extension, io.modelcontextprotocol/tasks: the blocking tasks/result method is replaced by polling via tasks/get, a new tasks/update carries client-to-server input, tasks/list is removed because, per the release notes, “it can't be scoped safely without sessions,” and servers may now return task handles unsolicited without a per-request opt-in. Anything built against the earlier experimental core Tasks API has to be migrated. Separately, Roots, Sampling and Logging are deprecated — still functional during the deprecation window, but new implementations should not adopt them. Whichever format carries the call, the lifecycle card above still applies: the wire format decides how a call is described, not whether it was authorized, validated, or safe to retry.

Not every wire format points at a tool. A2A standardizes agent→agent work for cross-vendor and cross-framework interoperability. An A2A Server publishes an Agent Card (§8): a JSON metadata document describing its identity, capabilities, skills, service endpoint, and authentication requirements, with support for digital signatures for integrity plus caching and version management — so a client agent can decide whether a remote agent fits before sending it anything. Work is then tracked as a Task (§4.1.1) with explicit TaskState values (§4.1.3): initial SUBMITTED and WORKING; terminal COMPLETED, FAILED, CANCELED, REJECTED; and interrupted INPUT_REQUIRED and AUTH_REQUIRED. Each TaskStatus (§4.1.2) carries the state, an associated message, and an ISO 8601 timestamp, and related tasks can be grouped via a contextId. Content is typed rather than free text: a Message (§4.1.4) has a messageId, a Role (§4.1.5) of USER or AGENT, and an array of Part objects (§4.1.6), where a part is text, raw (base64 bytes), a url reference, or structured data (JSON) — which is what lets two independently built agents agree on a format. For streaming (§4.2) there are two task-update event types — TaskStatusUpdateEvent for state transitions and TaskArtifactUpdateEvent for incremental Artifact (§4.1.7) updates — delivered via streaming operations, with the HTTP binding using Server-Sent Events. Errors are categorized as authentication, authorization, validation, resource, and system, with A2A-specific errors including TaskNotFoundError, PushNotificationNotSupportedError, UnsupportedOperationError, ContentTypeNotSupportedError, and VersionNotSupportedError. The same discipline is what a user interface needs from the harness: UI / event streaming means an SSE or WebSocket transport carrying an event envelope, with distinct event kinds for token deltas, progress updates, artifact updates, approval requests, cancellation, completion, and errors. An interface that only receives a final blob can't show progress, can't offer a cancel button, and has nowhere to render the approval gate the lifecycle card above depends on.
