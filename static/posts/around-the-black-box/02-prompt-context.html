Prompt, Context & Knowledge

What actually goes into the model's context this call and how it is selected and budgeted; how that context is kept clean as a run grows long; how a prompt's instructions are structured and ranked — and which content carries no authority at all; how a separate retrieval pipeline feeds grounded knowledge into that context without replacing it; and what that pipeline needs on either side of retrieval — getting usable text out of the source documents in the first place, turning a user's words into a searchable query, and holding a labeled test set that makes “retrieval quality” a number rather than an opinion.

Anthropic defines context as “the set of tokens included when sampling from a large language model (LLM)” — system instructions, tools, external data, message history, and examples, assembled by the Harness fresh each call. Their core principle: “find the smallest set of high-signal tokens that maximize the likelihood of some desired outcome.” This is not the same as state or memory — everything the application stores across turns and sessions (see State & Runtime) — context is only the slice of that store actually sent to the model this call. Because more is almost always available than fits, assembly is an explicit selection and ranking step: score the candidate items — memories, retrieved chunks, prior turns, tool results — and admit them in priority order until the budget runs out, rather than attaching whatever looks relevant and hoping it fits. Ordering is part of the design, not an accident of append order: where material sits in the window affects how strongly it influences the output, which is a general and well-observed effect, so placement is chosen deliberately. And give each component its own token budget — system, tools, memory, retrieved, history — with headroom reserved for the response itself, so a maximal input can never leave the model with no room to answer.

Context is not assembled once and left alone — it is maintained across a whole run, and both halves of that maintenance can fail quietly. Compaction should fire at a defined threshold — a set share of the usable window — so it is a predictable, testable event rather than an ad-hoc reaction to something feeling too long. Anthropic's guide describes pruning raw tool results deep in history as “one of the safest compaction techniques,” with summarizing-and-reinitiating for the rest. But compaction is lossy by definition, so you need a way to notice when something load-bearing was dropped: verify that the facts the run actually depends on survived the summary, and keep identifiers and links in the summary so any dropped detail can be re-fetched rather than guessed at. The other half is trust. Once assembled, an authored instruction and a scraped web page look like the same flat token stream, so label each span with its provenance and how far it is trusted — authored instruction, retrieved document, tool output, user paste. That labeling is what keeps the instruction hierarchy on this page workable in practice: tool output and retrieved content carry no instruction authority (see the Prompt Engineering card), and after everything lands in one window a provenance label is the only thing still saying so. Finally, bad content in context influences every later turn of the run, not just the turn it arrived in — so keep untrusted content clearly delimited, never let it slide into durable memory unreviewed, and keep the ability to drop or quarantine a poisoned span instead of carrying it forward for the rest of the session.

The OpenAI Model Spec (2025-09-12) ranks instruction authority in five levels: Root (the Spec itself, which cannot be overridden), then System (platform messages), Developer (API instructions), User (end-user instructions), and Guideline (default behaviors, implicitly overridable) — each level overrides the ones below it. Tool messages are not a rung on that ladder at all. The Spec lists them under “No Authority,” together with assistant messages, quoted/untrusted text, and multimodal data: “all other content (e.g., untrusted_text, quoted text, images, or tool outputs) should be ignored unless an applicable higher-level instruction explicitly delegates authority to it.” So only unquoted plain text in system, developer, and user messages can carry instruction authority; a tool result, a fetched web page, or a quoted passage is information, not a command — unless a higher-authority message explicitly delegates authority to that source. MCP's tools specification (revision 2026-07-28) reinforces the same point about a tool's own metadata: “clients MUST consider tool annotations to be untrusted unless they come from trusted servers.” And this hierarchy is not a prompt-injection security boundary — it is a provider-specific model-behavior convention implemented by training, not an enforced boundary. It contributes defense-in-depth, but it cannot substitute for real controls: authorization, isolation/sandboxing, input and output validation, and egress restrictions. Ranking your messages does not mean injection is handled. Within any single instruction, templates, delimiters, and a small set of diverse, canonical examples give the model structure it can parse reliably rather than an exhaustive list of edge cases — “examples are the ‘pictures’ worth a thousand words” for an LLM. Ask for structured output and validate it against a schema instead of parsing prose, and treat the prompt itself as versioned, tested code, not something edited freely in production.

RAG is a separate retrieval pipeline that feeds context — it doesn't replace it (see Data & Knowledge on the Foundations page for where it sits in the overall architecture). Source documents are parsed and chunked, embedded for semantic search and indexed for keyword/hybrid search, with the metadata and access controls (ACLs) of the original data carried onto every chunk — that offline build, the query preparation that precedes a search, and the labeled test set the metrics below are computed against are the subject of the Retrieval Pipeline card that follows. Retrieval then reaches the model by one of two distinct paths, and which one you pick is an architectural decision, not a detail. In application-controlled preprocessing, the application retrieves before inference and places the results into context deterministically: the model never chooses whether or what to retrieve, so the app owns both the query and the authorization check — the injection surface is narrower, latency is predictable, and the call is easy to observe. That is the classic retrieve-then-read shape. In model-selected retrieval via a tool call, the model decides mid-loop whether to retrieve and what to search for; this is more flexible and often better for open-ended work, but the query itself is model-generated, which widens the injection and authorization surface — a poisoned earlier turn can influence what gets searched for — and makes latency and observability harder to predict, because the number of retrievals isn't known up front. Either path, authorization must constrain the candidate set before or during retrieval, not after it. Filtering only at the end still lets the search rank over documents the user can't see, which leaks through result counts, ranking signals, and reranker behavior even when the forbidden documents themselves are dropped. So pre-filter the search to what the caller may see, then re-check permissions again before context assembly as defense-in-depth — and note that re-check matters more in the model-selected path, not less, precisely because the query was not app-authored. Attach citations either way, so every claim traces back to a source the user is allowed to read. Measure retrieval, don't assume it: recall@k (did the right chunk make the candidate set), MRR / nDCG (is it ranked near the top), citation precision (do the cited sources actually support the claim), groundedness (is the answer contained in retrieved context rather than invented), and freshness (how stale is the index). Those evals catch silent staleness or bad chunking before users do — but note that every one of them except freshness is computed against a labeled test set of queries paired with known-relevant documents, so building and maintaining that set is part of the work rather than a detail of it (see Retrieval Pipeline).

The RAG card describes the retrieval path; this is the machinery on either side of it, and it is where most retrieval quality is actually won or lost. Start with extraction, because you cannot chunk text you haven't got. PDFs, scans, and images need OCR; multi-column pages, tables, headers and footers, and reading order need layout extraction; slides and spreadsheets carry structure that naive text extraction destroys. This stage is the most failure-prone in the pipeline and it fails silently — a table flattened into a wall of numbers, or a two-column page interleaved line by line, produces chunks that embed cleanly, retrieve confidently, and mean nothing. Retrieval quality is capped by extraction quality, so parsing deserves its own validation — sample the extracted text, diff it against the source, check that tables and reading order survived — rather than being judged only by whether the final answer looked plausible. Chunking then splits on real structure (sections, rows, slides) rather than a fixed character count wherever it lands, and ACLs and metadata ride along onto every chunk. Next, at query time: the user's literal words are often the wrong search query. Rewriting turns a context-dependent utterance into a standalone one — resolving pronouns and references to earlier turns, normalising or expanding terminology, and optionally emitting several query variants to search in parallel. Decomposition splits a multi-part question into separate retrievals whose results are combined afterwards; a question like “how do X and Y differ” usually needs two retrievals, not one, because no single chunk covers both halves. Both tie straight back to the security point on this page: a rewritten or decomposed query is model-generated, so it remains untrusted input, and the authorization pre-filter has to apply to every sub-query independently — decomposition multiplies the queries, it does not dilute the check. Finally, the measurement itself: recall@k, MRR / nDCG, and citation precision are not free-standing numbers. They presuppose a labeled set of queries paired with known-relevant documents, and building one is real work — assembling queries that represent what users actually ask, judging which documents genuinely answer them, and keeping those judgements current as the corpus changes. Without that gold set, “retrieval quality” is an opinion rather than a measurement. It also buys you attribution: because the queries and expected documents are fixed, a drop after a parser or chunking change is visibly a pipeline regression, not a model one — which is otherwise very hard to tell apart.
