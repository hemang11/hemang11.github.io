State, Memory & Runtime

Context (Tab 02) is only the tokens sent into one model call. Everything on this page is what surrounds that call: the stores a run reads from and writes to, the infrastructure that lets a run outlive a single process, and the policies that decide what happens when a step fails.

Four distinct stores, not one bucket. All four hold memory — facts the agent has retained and can pull back in — which is a different thing from run state on the Durable Runtime card: state records where a run has got to, memory records what it knows. Working memory holds what the current session is working with: the in-flight facts, partial results, and intermediate findings this run has produced so far and may need again later in the same session. Semantic memory is facts/preferences that persist across sessions; episodic memory is retained experience from earlier runs, selectively recalled when it bears on the current one — last time this customer asked, the resolution was X — so it is a store the agent draws on, not a byproduct kept for graders; procedural memory is learned routines or skills — how to do something, distinct from a fact about the world. A write policy decides what's worth committing back to a store at all, and tags it with provenance (where it came from) so it can later be traced or distrusted. When two memories disagree, a conflict-resolution step decides which wins, rather than silently overwriting one with the other. TTL and forgetting policies expire or supersede stale facts so they don't quietly outlive their truth. Only the retrieved slice relevant to this turn is ever inserted into context — never the whole store. A separate point, and not what episodic memory is for: the complete trace of a run — the instrumented recording of what it did — is what evaluation and debugging read, which is a property of traces and observability rather than a definition of any memory store.

A run needs to survive longer than any one process. Modeling it as an explicit state machine — not implicit control flow buried in a function call stack — means progress can be checkpointed, so a crash or a pause resumes from the last checkpoint instead of restarting from scratch. Waiting on a webhook or a long-running external tool doesn't block a thread; it parks the state machine until the event arrives. Queuing and backpressure keep a traffic burst from taking the whole system down. Artifacts produced mid-run are stored durably, independent of whether the run's own process is still alive. Cancellation and deadlines mean a run doesn't keep executing past the point where its result is still wanted. Durability alone isn't correctness, though, and four more concerns come with it. Concurrency control: two steps of one run, or two runs touching the same record, can both read and both write and silently lose one update — so shared state needs locking or optimistic versioning (compare-and-set on a version number). Deduplication sits at the event layer: a queue that redelivers, a webhook that fires twice, or a retried trigger must not start the work twice, so incoming events carry an identifier the runtime records and drops on repeat — this is the message-level counterpart to idempotency keys on individual tool calls, which live on the Tools page. Compensation (the saga pattern): a run spanning many systems and many minutes can't be wrapped in one transaction, so steps that already committed need a defined compensating action — refund the charge, release the hold, cancel the booking, delete the created record — which failure runs backwards instead of leaving half-finished work behind. That works only where a semantically inverse operation genuinely exists, and plenty of committed steps have none: you cannot un-send an email, un-publish a post, un-disclose data, or un-notify a person. Assuming a universal undo is the actual design error. Where no inverse exists, rolling back is simply not available, and three other responses are. Prevention: gate the irreversible step behind approval, scope it as narrowly as possible, and order the run so irreversible work happens last, after everything reversible has already succeeded. Reconciliation: detect and record that state has diverged, rather than silently assuming a rollback worked. Forward recovery: take an action that reaches an acceptable end state — issue a correction, send a follow-up notice — instead of pretending to undo. State-schema migration: a run checkpointed last week may resume on this week's code, so persisted state carries a version and the runtime knows how to read or upgrade older shapes — otherwise a deploy quietly bricks every run still in flight.

Four separate policies, not one chained sequence. Retry needs error classification, idempotency, and backoff/jitter — it isn't just "try again." A circuit breaker stops calls to a dependency it's decided is unhealthy; it doesn't inherently notify a human. Escalation is its own policy, triggered by severity or repeated failure across any of the above.
